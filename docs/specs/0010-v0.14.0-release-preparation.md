# Specification: v0.14.0 Release Preparation and Integrity

Status: Release candidate prepared; final tag approval pending.

This revision supersedes the previously approved release preparation spec after independent review identified publish workflow and fail-open risks.

Target: `@reactive-skills/runtime`, `@reactive-skills/axi`, workspace metadata, release tooling, GitHub Actions publish workflow, release documentation, and generated changelogs.

Scope: `docs/scope/release-v0.14.0.md`.

Verification: The release-specific acceptance checklist is in Section 4, with regression coverage in `packages/runtime/tests/release-integrity.test.ts`, `packages/runtime/tests/release-bump.test.ts`, and `packages/runtime/tests/release-pull-request.test.ts`.

ADR needed: Yes, `docs/adr/0009-release-publish-integrity.md`.

## 1. Intent

Prepare a reviewable v0.14.0 minor release candidate for the merged bulk skill sync CLI feature.

Harden release paths so tag publication validates the exact release version, uses shell-safe tag handling, and cannot be silently triggered by candidate preparation.

The v0.14.0 tag remains unpushed until the user gives final approval because pushing it publishes packages and creates a GitHub Release.

## 2. Requirements

1. Set the root, runtime, AXI, and site package versions to 0.14.0.
2. Leave every per-skill `skill.yaml` version unchanged.
3. Generate release notes from commits after `v0.13.1` through the release candidate commit, and fail if the prior release tag is missing.
4. Update the root, runtime, and AXI README release banners and links to describe repeatable `--skill` selection.
5. Synchronize generated changelog content to the root and site using the existing generator.
6. Preserve archived runtime package tarballs byte for byte and produce a new 0.14.0 tarball.
7. Update internal release guidance to explain package versus skill versions, release tag validation, and the publish-triggering tag push.
8. Validate release tags as exact `vMAJOR.MINOR.PATCH` versions and require equality with root, runtime, AXI, and site package versions.
9. Pass the release tag to shell commands through an environment variable and quote it; do not interpolate a GitHub expression directly into shell source.
10. Make changelog synchronization, build, and pack failures exit nonzero without a success message.
11. Use candidate preparation without creating or pushing a release tag.
12. Remove the legacy one-command path that commits, replaces a tag, and pushes both `main` and a release tag.
13. Allow only explicit release tag pushes to trigger publishing; remove `workflow_dispatch`.
14. Require the tag target to be the merge commit of a merged pull request into `main`, and run CI tests before using package credentials.
15. Require pull requests and both Node-version CI matrix checks on `main`, with zero required reviewer approvals while the repository has one collaborator.
16. Reject explicit bump versions that are equal to or lower than the current package version.
17. Add verification coverage for invalid and mismatched tags, merged-PR publish gating, monotonic versions, release preparation failure paths, and the absence of an automatic publish path.

## 3. Decisions

The user selected 0.14.0 as the package release version.

The runtime package manifest remains the version seed for `pnpm bump:minor`.

The previous matching release tag, `v0.13.1`, remains the lower bound for generated release notes.

Individual skill versions describe skill releases and remain independent of workspace package versions.

The release banner headline comes from the merged bulk sync CLI change at commit `97cbf1c`.

Independent review found a shell injection risk in `.github/workflows/publish.yml`, insufficient tag and package version checks, fail-open behavior in `bump-version.js`, and an auto-publishing `release.js` path.

Decision: remove `release.js` and the `release:*` package scripts, retain `bump:*` as the deterministic candidate preparation tool, and publish only by explicitly pushing a validated tag that targets the exact merge commit of a merged pull request into `main`.

Runner-up: retain the release helper behind a required `--publish` flag, which preserves convenience but leaves one command capable of committing and pushing the release.

The user approved removing the one-command publisher because it duplicates agent orchestration and bypasses the review boundary.

Alternatives rejected: deriving notes from an arbitrary recent commit count can include already released changes, and rewriting every skill version conflates separate version domains.

## 4. Acceptance Criteria

1. Root, runtime, AXI, and site package manifests report version `0.14.0`.
2. Per-skill `skill.yaml` files have no version changes.
3. The generated 0.14.0 changelog section contains commits after `v0.13.1` and includes the bulk sync feature.
4. Root, runtime, and AXI README banners and release links reference `v0.14.0` and describe bulk skill selection accurately.
5. The site changelog is regenerated from the package changelog by the existing generator.
6. Existing runtime tarballs retain their original checksums, and `reactive-skills-runtime-0.14.0.tgz` exists.
7. The publish workflow accepts only an exact `vMAJOR.MINOR.PATCH` tag whose version matches all four workspace manifests.
8. The publish workflow passes the validated tag to `gh release create` through a quoted environment variable, with no raw GitHub expression embedded in shell code.
9. The publish workflow runs only on tag pushes and rejects release commits that are not the merge commit of a merged pull request into `main`.
10. The workflow's runtime and AXI tests pass before package credentials are used.
11. Missing prior release tags and changelog sync, build, or pack errors stop candidate preparation with a nonzero exit status and no completion message.
12. Explicit bump versions equal to or lower than the current package version fail before writing release metadata.
13. Candidate preparation cannot create or push a release tag, and the legacy `release:*` automatic publish path is removed.
14. Verification covers tag format and version mismatch rejection, merged-PR gating, version monotonicity, missing prior tags, propagated generation failures, and the release publish trigger.
15. The `main` branch requires a PR and the `CI` checks for Node 22 and Node 24, with no reviewer approval requirement while the repo has one collaborator.
16. Internal release guidance documents package and skill version domains, strict tag validation, a repack after README edits, and the reviewed tag push as the publish action.
17. Workspace build, runtime tests, AXI tests, docs checks, prose checks, release tooling tests, and final diff review pass.
18. The final reviewed candidate contains no pushed `v0.14.0` tag.

## 7. ADR

The publish workflow holds package publishing credentials and GitHub release write permission, so validating its input and separating candidate preparation from publication is a release security boundary decision.

ADR `docs/adr/0009-release-publish-integrity.md` records the selected tag validation and publish gate.

This specification's acceptance criteria are the release-specific checklist; there is no separate `verify.md` copy to drift.

## 8. Consequences

The four workspace package versions remain aligned while individual skill releases stay independently versioned.

Generated notes describe only commits after the prior package release tag.

Candidate preparation is reviewable without publishing, and the publish workflow refuses malformed or mismatched tags before using release credentials.

The user approved this revised spec, and the release candidate is prepared with the `v0.14.0` tag still unpushed.
