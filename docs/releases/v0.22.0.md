# Reactive Skills v0.22.0 release notes

This 0.x minor release includes breaking changes; review the migration notes before upgrading.
It updates `@reactive-skills/runtime` and `@reactive-skills/axi` together from `0.21.0` to `0.22.0`.
It binds AXI skill runs to a canonical workspace, lists the jobs of every known workspace in the dashboard, adds `workspaces register` and `workspaces list`, restricts the telemetry server to local `Host` headers and allowlisted origins, makes MCP receipt paths workspace-relative, and adds an experimental runtime-executed state type.
These notes describe the release candidate; publication follows a merged release pull request and a separate `v0.22.0` tag push.

## Breaking changes

- **Workspace-relative MCP receipt paths:** Receipt `projectionsWritten` entries from `reactive_emit_signal` and `reactive_respond_human` are now paths relative to the MCP server's workspace (the `workspace` that `reactive_capabilities` reports), for example `.docs/jobs/default/summary.md`, instead of absolute paths. Resolve them against that workspace, or pass `receipt_paths: "absolute"` to keep absolute paths. Saved receipts in the ledger keep absolute paths, so a keyed retry returns the form the retry requests. Capability: `receipt.relative_paths`. A path outside the workspace stays absolute ([change](https://github.com/Reactive-Skills/reactive-skills/pull/120)).

| Tool | Option | Default now | Other values |
|---|---|---|---|
| `reactive_emit_signal`, `reactive_respond_human` | `receipt_paths` | `relative` | `absolute` (previous receipt paths) |

Signal and evidence contracts are unchanged: the same signals, payloads, guards and receipts.
The `return_view: "none"` and `output: "legacy"` options introduced in 0.21.0 are still accepted by this release.

## Behavior changes to review

These changes were merged as fixes and additions rather than as breaking changes, but they change what existing AXI and telemetry integrations observe.
Review each one before upgrading scripts, agents and hosting configurations.

### Workspace binding

AXI commands now bind a skill run to a canonical workspace, which owns the `.reactive` ledger, run metadata, evidence and generated `.docs` projections ([change](https://github.com/Reactive-Skills/reactive-skills/pull/136)).

- Pass `--workspace <directory>` or set `WORKSPACE_DIR` to choose the workspace explicitly; the flag takes precedence over the environment variable, and both accept an existing directory (relative paths resolve against the caller's directory).
- The CLI resolves symlinks and records the canonical absolute path as `workspaceRoot` in each new job's `job.json`. State diagnostics and job listings show it, so an agent can start a run, change directories and resume the same run.
- Legacy jobs without a recorded `workspaceRoot` stay usable. `context.workspace_root` stays descriptive and never changes the runtime workspace.
- New runs start in the caller's workspace. For existing runs, a store that contains the caller wins, with a warning when other known stores also hold the job. Outside every candidate store, a single matching known store supports resume, and several matches require `--workspace` or `WORKSPACE_DIR`.
- AXI output now includes workspace diagnostics, which adds 119 normalized bytes per operation to the pinned AXI stdout expectations in the transport benchmark. The historical baseline and the MCP and SDK expectations are unchanged. Update any script that matches AXI output byte for byte.

See the [workspace binding reference](../workspace-binding.md) for the full selection rules.

### Unknown jobs are refused

Named `state` and ordinary `emit` calls now refuse a job that no known store holds instead of silently starting a fresh run at the initial state.
Use `invoke` to start a named run; scripts that relied on a first `emit` to create a run must call `invoke` first.
Explicit evidence import, including folded import-and-emit, keeps its existing run registration within the selected workspace.

### Reset and purge need an explicit workspace outside the selected store

`reset` and `reset --purge` act only on a store that contains the caller's directory, or on an explicit `--workspace` or `WORKSPACE_DIR` root.
When the only candidate is another known store, they fail and name the store with the `--workspace` flag to pass.
`reset --purge` deletes only the selected workspace's skill store and never removes a sibling legacy store beside the installed skill.
Cleanup scripts that ran from an unrelated directory must pass `--workspace`.

### The dashboard lists every known workspace

`dashboard` now lists the jobs of every known workspace (stores that contain the caller first, then ancestors and recorded roots) instead of only the directory it was started in, and shows each job's workspace root ([change](https://github.com/Reactive-Skills/reactive-skills/pull/137)).
A skill and job identifier held by several workspaces is listed once per workspace, `/state` accepts an optional `workspaceRoot`, and event `target` filters accept an optional `<workspace-root>/` prefix; an omitted root resolves to the first workspace that holds the job, so existing single-workspace URLs keep working.
`--workspace` or `WORKSPACE_DIR` still limits the dashboard to one store and records nothing.
Custom clients that key jobs by skill and job identifier alone should also key by workspace root.

A workspace is known when it contains the caller's directory, when a skill-targeted CLI run has recorded it in the per-user workspace catalog, or when `workspaces register` recorded it.
Stores created before the catalog existed stay out of the dashboard until one of those happens, so after upgrading, register your existing workspaces once:

```bash
reactive-skills-axi workspaces register --scan <parent> --dry-run
reactive-skills-axi workspaces register --scan <parent>
reactive-skills-axi workspaces list
```

- `--scan <parent>` (repeatable) searches below the parent for workspace roots that hold `.reactive/skills`; `--max-depth <n>` (default 3) limits the depth. Explicit workspace paths register without a search.
- `--dry-run` reports what would be added and writes nothing. `--json` prints the report as JSON.
- The report lists `added`, `already_known` and `skipped` roots. Registering twice is safe, and stores are never opened, changed or moved; only the catalog is written.
- `workspaces list` prints each recorded root and whether it still holds a store, and fails on a malformed catalog entry like every other command.

Registration is a one-time step for older jobs; new runs record their workspace automatically ([change](https://github.com/Reactive-Skills/reactive-skills/pull/138)).

### The telemetry server answers only local requests

The telemetry broker behind `dashboard` now refuses requests whose `Host` header is not `localhost`, `127.0.0.1` or `[::1]` (any port) with `403`, on every route including `OPTIONS` and the event stream.
It sends CORS headers only to `https://reactive-skills.com` and to `http://localhost` or `http://127.0.0.1` origins on any port; other origins receive no CORS headers, and requests without an `Origin` header are served unchanged.

- `dashboard --host 0.0.0.0` still listens on every interface, but the broker is reachable only through `localhost` or `127.0.0.1`, and the printed `0.0.0.0` URL is refused. Other machines can no longer reach it by address or hostname.
- A browser page served from another origin, including a self-hosted copy of the site, can no longer read the broker. Serve it from `localhost` or `127.0.0.1`, or from `https://reactive-skills.com`.
- These rules are a defense against browsers and DNS rebinding. They do not stop a non-browser client that can reach the bound address and sends a local `Host` header, so keep the default `127.0.0.1` binding unless the network is trusted. The exact rules are in [spec 0005](../specs/0005-multi-job-telemetry-broker.md).

The broker also opens event stores read-only, tails only the jobs a connected dashboard tracks, and skips a failing root, skill or job with a once-per-label warning instead of aborting the refresh.

### Bootloader retrieval is required

Bootloader guidance advances to `1.0.1` ([change](https://github.com/Reactive-Skills/reactive-skills/pull/133)).
Generated retrieval references now require using the skill, reading all three retrieval alternatives before judging availability, and stopping with the exact missing prerequisite or failure when none works.
The served instructions open with three progressive-disclosure lines and treat a routing failure as part of skill execution rather than a reason to skip the skill.
`init` and the missing-document migration scaffold add a discovery hint to the existing `description` field.
The package version change alone does not rewrite installed skills: the existing migration helper regenerates canonical pointers, and `validate` reports stale ones.
Refresh the retrieval reference in authored skills and in any template maintained outside this repository to pick up the new wording.

## New features

- **Workspace binding, `workspaces register` and `workspaces list`:** described under the behavior changes above. Fixes issues 14 and 26 ([workspace binding](https://github.com/Reactive-Skills/reactive-skills/pull/136), [registration](https://github.com/Reactive-Skills/reactive-skills/pull/138)).
- **Multi-workspace telemetry:** the broker accepts a list of workspaces, identifies each target by workspace root, skill and job, and reports `workspaceRoot` in catalog jobs, `/state` responses and event envelopes ([change](https://github.com/Reactive-Skills/reactive-skills/pull/137)).
- **Runtime-executed states (experimental):** a manifest that requires the `state.runtime_actions` capability can declare `runtime_action` on a leaf state, and the runtime runs the declared command, path check, schema check or expression without a model turn and records the result as ledger evidence. The shape may change; see [runtime-executed states](../runtime-actions.md) ([change](https://github.com/Reactive-Skills/reactive-skills/pull/121)).
- **Shorter bootloader:** two pairs of overlapping bootloader sentences are merged without removing an instruction ([change](https://github.com/Reactive-Skills/reactive-skills/pull/120)).
- **Site and research:** the documentation site gets a redesigned homepage, docs layout, registry, blog, mods, privacy, telemetry and error pages and agent-first skill entry paths, and an adherence harness and pilot compare flat and reactive skills under context pressure. Neither changes the published packages' interfaces.

## Upgrade checklist

1. Once published, upgrade both packages together with `npm install @reactive-skills/runtime@0.22.0` for SDK applications and `npm install -g @reactive-skills/axi@0.22.0` for global CLI installations, or run `npx -y @reactive-skills/axi@0.22.0 <command>` directly.
2. Keep Node.js at `22.13.0` or newer, and rerun `setup` for harness configurations pinned to an earlier AXI version.
3. Resolve MCP receipt `projectionsWritten` paths against the workspace that `reactive_capabilities` reports, or pass `receipt_paths: "absolute"`; check `receipt.relative_paths` before relying on the new default.
4. Pass `--workspace` or set `WORKSPACE_DIR` in scripts and agent instructions that run skills from a directory other than the project, and start named runs with `invoke` before any `state` or `emit`.
5. Pass `--workspace` to `reset` and `reset --purge` when you run them from outside the store you mean to reset.
6. Run `reactive-skills-axi workspaces register --scan <parent> --dry-run`, review the `added` list, then run it without `--dry-run` so the dashboard lists older jobs.
7. Open the dashboard through `localhost` or `127.0.0.1`, and stop relying on `dashboard --host 0.0.0.0` for access from other machines.
8. Update tests that compare AXI output byte for byte to allow the added workspace diagnostics.
9. Regenerate retrieval references in authored skills with the migration helper to adopt the `1.0.1` bootloader wording.

Individual skill versions are independent of these workspace package versions and do not change in this release preparation.
