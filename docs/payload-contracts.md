# Payload contracts and guard inspection

Runtimes advertising `state.payload_contracts` support optional authored payload requirements on each transition.
Authors relying on these structural checks or payload guidance should require `state.payload_contracts` through `runtime_requirements.required_capabilities` during runtime preflight.
They help an agent build a submission; the original guard expression, guard function, judgment, evidence verification and human approval rules still decide the transition.
No contract is inferred from a complex expression or generated by a model.

```yaml
transitions:
  TEST_RAN:
    target: REFACTOR
    guard: event.payload.exit_code === 0
    payload_contract:
      fields:
        exit_code: { type: number, const: 0 }
      relationships: []
      evidence_source: test command result
      refusal_hint: Run tests and submit the numeric exit code.
```

`fields` declares top-level payload names and their types: `string`, finite `number`, `boolean`, `object`, `array` or `null`.
Fields are required unless `required: false`; an optional field is checked when present.
`const` accepts a primitive value matching the declared type, including `null`.
Extra payload fields remain allowed, so an intentionally incomplete contract cannot remove another requirement enforced by a guard.
For nested values, declare the containing object or array and describe the required relationship in `relationships`.
Existing guards enforce those authored relationship descriptions; they are not executable expressions or substitutes for guards.
`evidence_source` describes where to obtain the evidence and does not authenticate that evidence or change evidence-reference resolution.
`refusal_hint` gives a concise recovery action.
All four contract keys are required; `fields` and `relationships` may be empty.

Manifest validation rejects unknown declaration keys, invalid types, incompatible constants and invalid field names.
It also rejects provable contradictions between a declared field and a guard consisting entirely of one strict equality against a JSON primitive, such as a contract requiring `exit_code: 0` with `guard: event.payload.exit_code === 1`.
That bounded consistency check neither derives missing fields nor certifies equivalence with arbitrary guard code.
Contract review remains the author's responsibility.

Compact views and legacy XML replace inline guard source with the authored contract only for transitions declaring it.
Absent a contract, exact inline conditions remain visible and opaque guard functions retain their module path and explicit inspection guidance.
Every condition retains its owning state, signal and target in leaf-to-ancestor order, including repeated signal names.
A structural contract refusal continues ancestor fall-through using the same signal and verified evidence.
Valid structural input always reaches the existing guard evaluator; an incomplete contract cannot turn a failed guard into an approval.
Contract failures are recorded through the existing guard/refusal events and carry the field requirement and refusal hint.
Failed original guards retain their reason and gain the authored hint and inspection guidance.
No additional event type, projection or ledger scan is introduced.

Inspect the exact owning transition when its authored requirements are insufficient:

```bash
reactive-skills-axi inspect skills/my-skill --state GREEN_CODE --signal TEST_RAN
```

With MCP, call `reactive_inspect` with `{"skill":"my-skill","state":"GREEN_CODE","signal":"TEST_RAN"}`.
Both selectors are required together.
The response contains `state`, `signal` and the complete transition declaration, including any exact `guard` expression and authored contract.
For `guardFunction`, `guard_source` contains the module text; inspection never imports or executes it and refuses source paths or symlinks outside the skill directory.
Targeted inspection reads the manifest currently on disk without opening a run, emitting events or executing lifecycle hooks.
MCP `job_id` does not change this manifest-level inspection.
Omitting the selectors preserves the existing whole-skill inspection behavior.
SDK consumers can call `inspectTransitionGuard(manifest, skillDir, state, signal)` to inspect the declaration loaded by their engine.

## Cost measurement

Run `pnpm --filter @reactive-skills/runtime exec tsx scripts/benchmark-payload-contracts.ts` from the workspace root.
The offline probe copies the pinned public TDD fixture to temporary directories and compares the same `GREEN_CODE` state with and without an authored contract.
It counts UTF-8 bytes of actual MCP response text plus JSON request arguments, including both sides of optional guard inspection.
It excludes JSON-RPC framing, tool definitions, process startup and model work; bytes are not tokens.

| Presentation | Initial delivery | Optional inspection | Total with inspection |
|---|---:|---:|---:|
| Exact TDD guard | 1,552 B | 167 B | 1,719 B |
| Authored TDD contract | 1,743 B | 334 B | 2,077 B |

For this short guard, authoring metadata adds 191 B before inspection and 525 B when compared with exact initial delivery requiring no inspection.
It supplies explicit typing and recovery guidance but does not reduce this example's bytes.
Longer guard implementations can yield smaller initial views; their net cost must include any inspection requests and responses.
No catalog-wide or end-to-end model savings claim follows from this probe.

On Node v22.23.3/Linux with warm filesystem caches, 100 samples after ten warmups measured authored structural validation at 0.000613 ms p50 / 0.000875 ms p95 and complete compact view construction at 0.203840 / 0.317987 ms.
Complete refused-signal handling, including existing persistence, measured 6.110257 / 7.816677 ms.
These isolated measurements are not cold-start or external judgment latency measurements.
